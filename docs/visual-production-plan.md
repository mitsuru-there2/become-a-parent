# ビジュアル制作計画

作成日：2026-09-22  
対象：イベント、判断、子どもの代表状態、年代別情景のゲーム内ビジュアル

## 1. 目的

正式HERO `assets/marketing/hero.png` の画風を基準に、ゲーム内の文章を補助する画像を段階的に整備する。

今回の方針変更により、子どもの状態画像は大きな情景画ではなく、小さなプロフィール画像のような正方形アイコンとして制作する。数値や内部状態を直接示すのではなく、公開されている代表状態を見分けるための図柄として使う。

## 2. 現状と制作対象

### 既存の試作

| 種類 | ファイル | 扱い |
| --- | --- | --- |
| イベント | `assets/scenes/generated/event-washing-machine-v1.png` | イベントダイアログ用の方向性確認・候補 |
| 判断 | `assets/scenes/generated/decision-branch-v1.png` | 判断画面用の方向性確認・候補 |
| 子どもの状態 | `assets/scenes/generated/child-state-curious-v1.png` | ワイド情景の参考。プロフィールアイコンとしては使用しない |

### コンテンツ規模

- 自動イベント：`config/events.json` に72件。善悪・年齢・題材が異なる。
- 現行の判断：5ステージ × 17ルート × 10判断で850件。判断の選択肢には画像IDを指定できる。
- 判断カテゴリ：教育・進路、家庭生活、実家、遊び・放課後、仕事・家計の5分類。
- 子どもの代表状態：12特性の代表状態＋特性がまだ低いときの「成長中」の計13種類。
- 年代別情景：乳児、未就学、小学生、中学生、高校生相当、進路準備期の6種類。

## 3. 共通アート方針

- `assets/marketing/hero.png` を毎回のスタイル参照画像にする。
- 黒地と白主体の1bitドット表現、粗いドット、段差のある輪郭、規則的なディザを維持する。
- 文字、UI枠、タイトル、ロゴ、透かしは画像に入れない。文字情報はアプリ側で表示する。
- 写実、フルカラー、グラデーション、強いホラー表現は採用しない。
- 日常の困りごとを少し誇張するが、子どもを侮辱したり、健康・発達・性格を現実の診断のように見せたりしない。
- 画像生成は組み込みの画像生成ツールで、原則1プロンプト1アセットとする。CLIの一括生成は、別途明示的に選択した場合だけ検討する。
- 生成後は必ず、縮小時の判読性、人物の輪郭、HEROとのコントラスト、余白、誤読の有無を確認する。

## 4. アセットの設計

### 4.1 イベント画像

72件すべてに別画像を作るのではなく、まずイベント本文を題材ファミリーに分類し、代表画像を再利用する。

初期目標は12〜16枚程度。

| 題材ファミリー | 例 |
| --- | --- |
| 家計・援助・仕事の成果 | 実家からの援助、報奨金、初めての収入 |
| 休息・回復・疲れ | 赤ちゃんの睡眠、親の疲労、実家の回復 |
| 乳幼児の日常 | 夜泣き、ティッシュ、第一歩、ポケットの収集物 |
| 学校・学び | 友だち、宿題、図書館、学校行事 |
| 家族の距離と会話 | ノック、夕食、家族の外出、すれ違い |
| 工作・発明 | 火山、ロボット、発明賞、修理 |
| 音楽 | セッション、アンプ故障、演奏会 |
| スポーツ | リレー、遠征、チーム道具 |
| 旅・交流 | 海外の手紙、野外交流、予定外の駅 |
| 店・料理・実家の技 | 屋台、店の注文、レシピ、機械故障 |
| 自立・進路・成人後 | 面接、進学、工房、最初の電話 |
| 隠し特性から生じる小事件 | 手作りゲーム、班の相談役、提出前夜 |

仕様案：

- マスターは横長の情景画。イベントダイアログ上部の横長トリミングで主題が失われないよう、人物と主要物を中央の安全領域に置く。
- 既存の `event-washing-machine-v1.png` を「日常の小さな災難」ファミリーのパイロットとして評価する。
- `kind` の善悪はアプリ側の枠色・ラベルで示し、画像自体に赤・緑の色分けは持たせない。
- 同じ題材でも、条件や効果が違うだけのイベントは原則同じ画像を使う。

### 4.2 判断画像

850件を個別制作しない。まず5カテゴリの入口画像と、17ルートの特徴画像を制作し、判断の選択肢から再利用する。

初期目標は22枚程度（カテゴリ5枚＋ルート17枚）。必要な場合だけ、後から代表的な判断の個別画像を追加する。

| 層 | 制作内容 | 用途 |
| --- | --- | --- |
| カテゴリ | 教育・進路、家庭生活、実家、遊び・放課後、仕事・家計 | マップやカテゴリ入口 |
| ルート | `config/decisions.json` の17ルートを直接参照して制作 | ルートの見分け、判断詳細 |
| 個別判断 | 説明だけでは意味が伝わりにくい重要判断のみ | 将来の追加枠 |

ルート画像は、数値効果の強さや「正解」を表すのではなく、題材と生活の雰囲気を表す。左右の選択を画像内で優劣づけない。

### 4.3 子どもの代表状態アイコン

子どもの状態はプロフィール画像に近い、小さな正方形アイコンとして制作する。

初期目標は13枚。

| IDの考え方 | 代表状態 | 図柄の方向性 |
| --- | --- | --- |
| `growing` | 成長中 | 子どもの顔または上半身と小さな芽・積み木 |
| `music` | 音楽家 | 楽器または音符を持つ子ども |
| `sports` | スポーツ選手 | ボールや走る姿勢 |
| `maker` | 発明家 | 工作物、歯車、道具 |
| `gamer` | ゲーマー | 手作りゲーム機やコントローラー |
| `researcher` | ガリ勉 | 本、虫眼鏡、観察対象 |
| `writer` | 作家 | ノート、鉛筆、物語の小道具 |
| `quiet` | 引きこもり | ひとりの読書や静かな部屋。否定的な表情にしない |
| `social` | 交流上手 | 子ども同士の小さな輪 |
| `leader` | リーダー | 旗や先頭に立つ姿勢 |
| `reliable` | しっかり者 | 整理された道具、世話をする姿勢 |
| `escape` | 逃げ上手 | 物陰や抜け道を使う、軽いコミカル表現 |
| `challenger` | 挑戦者 | 小さな山、階段、何度も試す姿勢 |

仕様案：

- マスターは256×256pxの正方形PNG。実表示は家族カードで40〜48px、詳細で64〜96px程度を想定する。
- 顔・髪・上半身または象徴物を72〜80%の安全領域に収める。細かい背景や長い文字は入れない。
- 年齢を固定しすぎず、0〜20歳の表示期間で破綻しない、簡素なプロフィールシルエットにする。
- 同じアイコンを状態カードと詳細パネルで使い、CSSで縮小する。用途ごとの別絵は最初から作らない。
- 現行の「余裕」「父との関係」「母との関係」の3段階観察アイコンは、D-079のSVG表示を維持する。代表状態アイコンと混同させない。
- アイコンは代表状態の演出用であり、非公開の特性値や子どもの真値を数値化・推測させない。

### 4.4 年代別情景

イベント・判断・状態アイコンの制作が一巡した後、6年代の情景画像を制作する。これは子どものプロフィールアイコンとは別物で、画面の情景説明や導入に使う。

## 5. 実行フェーズ

### Phase 0：素材台帳と表示確認

1. 72イベントを題材ファミリーへ分類する。
2. `config/decisions.json` の5カテゴリ・17ルートと、13の代表状態IDを台帳にする。
3. イベントの横長トリミング、判断の詳細表示、プロフィールアイコンの表示場所をブラウザで確認する。
4. 既存3枚を候補として残し、最終採用前の基準画像とする。

完了条件：各画像に「どの画面で、何を伝えるか」が1行で対応している。

### Phase 1：子どもの状態アイコンを優先制作

1. `growing`、`music`、`maker`、`quiet` の4枚をパイロットにする。
2. 48px前後まで縮小して、顔・象徴物・白黒の抜けが判別できるか確認する。
3. 採用した線の太さ、顔の比率、背景の密度を基準化する。
4. 残り9枚を同じ仕様で制作する。
5. 現在の `child-feature-placeholder.svg` を置き換えるための画像参照・表示サイズ変更を別作業として実装する。

### Phase 2：イベント代表画像

1. 題材ファミリーごとに最も読みやすいイベントを1〜2件選ぶ。
2. 12〜16枚を生成し、イベントダイアログの横長表示で確認する。
3. 72件へ画像IDを割り当てる。画像が不要な文章イベントは無理に追加しない。
4. `visuals` の登録、イベントの `visual` 参照、画像URLの読み込み対象を実装する。
5. 0件・1件・複数件のイベント表示と、善悪の枠色が崩れないことを確認する。

### Phase 3：判断代表画像

1. 5カテゴリの入口画像を制作する。
2. 17ルートの題材画像を制作する。
3. 850件の判断へカテゴリまたはルート画像を再利用で割り当てる。
4. 説明が抽象的、分岐の意味が重要、またはユーザー評価で区別しづらい判断だけ個別画像を追加する。
5. マップの画像、判断詳細の画像、モバイル表示の縮小を確認する。

### Phase 4：年代別情景と追加パック

1. 6年代の情景画像を制作する。
2. `assets/scenes/generated/` の試作を、採用版のディレクトリ構成へ整理する。
3. 追加パックの画像は、本編の画像IDや画風を再利用できるか確認してから増やす。
4. DLCごとに独立した画像を増やしすぎず、追加題材の代表画像を優先する。

### Phase 5：総合確認

- 画像の欠落、壊れたパス、代替テキスト不足がない。
- 画像を付けたイベント・判断・状態が、本文の意味と一致している。
- 同じ画像の再利用が、情報不足や誤解を生まない。
- 48px程度の状態アイコンでも、隣接する状態と取り違えにくい。
- `bun run check`、`bun run test`、実行中サーバーでの `bun run test:browser` を順に実施する。
- 画像だけを追加した段階では設定変更を行わず、統合時にコンテンツ検査と画面検証を行う。

## 6. 保存・命名・統合方針

制作中の画像は、既存HEROや採用済み画像を上書きしない。

```text
assets/scenes/generated/
  events/
    event-<family>-v1.png
  decisions/
    decision-category-<id>-v1.png
    decision-route-<id>-v1.png
  child-states/
    child-state-<id>-v1.png
  stages/
    stage-<id>-v1.png
```

採用後は、`config` の `visuals` に一意のID、画像パス、代替テキストを登録する。判断画像は選択肢の `visual`、自動イベント画像はイベントの `visual`、年代別情景は `scenes.<id>.visual` から参照する。

現在の `ContentImage` はHEROの読み込みを前提にしているため、統合時には新しい画像群もビルドに含める画像マニフェストまたはglobの設計を合わせて更新する。設定JSONや生成ファイルを直接手編集で増やす場合は、既存のスキーマ検査と生成手順に従う。

## 7. Lunaの推奨effort

### 推奨値

この計画を一通り実行する場合の標準は、**GPT-5.6 Luna / medium effort** を推奨する。

理由は、作業の中心が「台帳からの分類」「定型的なプロンプト作成」「画像の確認」「ファイル整理」という、Lunaに向いている集中的・反復的な作業だからである。OpenAIの公式ガイドでも、Lunaは focused or repetitive tasks 向けの高速・経済的なモデルと説明され、effortはまず低めから始め、必要なときだけ上げる方針が案内されている。

作業別の目安：

| 作業 | 推奨effort | 理由 |
| --- | --- | --- |
| 1枚ずつの画像生成、候補整理 | low〜medium | プロンプトが定型的で、画像品質は参照画像とプロンプトの影響が大きい |
| 13アイコンやイベント台帳の整備 | medium | 題材の重複・命名・再利用の判断がある |
| 設定JSON、画像読み込み、UI統合 | medium〜high | 複数ファイルの参照関係と検証が必要 |
| 大規模な不具合調査や設計変更 | high | コード・仕様・保存互換性を横断して確認する必要がある |

通常はmediumで開始し、結果が不足した場合にだけhighへ上げる。xhigh以上は、今回の画像制作そのものには推奨しない。effortを上げても画像生成結果が自動的に良くなるわけではないため、まず参照画像、構図、縮小時の見え方、再利用単位を改善する。

参照：[Managing usage with GPT-6 Astra in Work and Codex（OpenAI公式）](https://help.openai.com/en/articles/20001516-managing-usage-with-gpt-6-astra-in-work-and-codex)

## 8. 今回の計画で決めていないこと

- 13アイコンの正式IDを、既存の `child_identity.feature` のIDへ完全に合わせるか。
- 子どものアイコンを家族カードのどの位置まで拡大するか。
- 850件の判断すべてに、カテゴリ画像・ルート画像・個別画像のどの優先順位で割り当てるか。
- 画像をPNGだけで配布するか、表示用にWebP等を併記するか。
- 生成画像の最終採用者と、候補を何枚まで残すか。

これらはPhase 0の表示確認と、Phase 1の4枚パイロットを見てから決める。
