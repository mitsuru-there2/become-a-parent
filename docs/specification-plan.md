# 仕様策定計画

作成日：2026-09-12。更新日：2026-09-14。状態：SP-01〜09の仕様策定を完了。2026-09-14の実装依頼（D-017）でP-TEXTへ移行した。現行の実装・検証状況は[開発計画](development-plan.md)を参照する。以下は仕様策定時の成果と進め方の記録。

この文書は開発計画のP-SPECを分解し、「どの順に、どうやって仕様を決めるか」を管理する。決まったゲームの振る舞いは[SPEC](SPEC.md)、重要な理由は[意思決定記録](decisions.md)、残った論点は[未決事項](open-questions.md)へ反映する。詳細仕様の現行内容はSPECとその分冊に置く。策定と実装・プレイテストの完了は区別する。

主軸は案2のコメディに決定済み（Q-013、D-008）。ボードゲーム的な偶然、モノクロでシュールな表現を採用する。半年単位・全40ターンも決定済み（D-010）。SP-01の5本・共通家庭・親の5評価軸もユーザーが採用した（D-013）。残る仕様は委任に基づいて具体化した（D-014）。

## 到達点

少数の基本パターンについて、子どもの0〜20歳から親の老後・最期・評価まで、実装者が追加のゲームルールを推測せずにCLIを作れる仕様を用意する。

人生全体、子ども1人、少数のバリエーション、CLI、AIエージェントによるテストプレイは既定の方針として引き継ぐ。パラメータ、イベント、初期値、式、技術契約の初版はSPECの分冊に記載済み。数値は検証後に調整する仮値として管理する。

## 各ステップ共通の進め方

1. 対象の未決事項を確認し、推奨案と具体例を作る。すべてをユーザーへの質問から始めない。
2. 案を比較する必要がある点だけ、選択によって遊びがどう変わるかを説明する。通常の可逆的な設計判断は理由を記録して進め、重要な好みや合意方針の変更が必要なときに確認する。
3. 表・文章例・手計算を使い、通常のケースと問題が起きるケースを照合する。
4. 決まった内容をSPECへ反映し、関連Qの解決済み部分と残りを記録する。下記の完了条件を満たしたら、根拠へのリンクとともにステップの状態を更新する。

仕様上の処理と、後で調整する数値を区別する。仮の数値でも、初版で使う値、期待する挙動、見直す条件を置く。必須処理の空欄を「試作で考える」として残さない。一方で、実装前の机上確認をプレイテスト済み・面白さ検証済みとは呼ばない。

各ステップはテーマごとのまとまりとして進めるが、一律の承認ゲートにはしない。新たな問題が出たら必要な前段に戻り、影響範囲だけを再確認する。

## SP-01：基本パターンと評価方針

**対象**：Q-013の主軸・対象者は決定済み。SP-01で扱うのは、最初に比較するパターンの数と題材、共通の初期条件と変える条件、プレイヤーに感じてほしい迷い、幸福として扱うこと・扱わないこと。ここではスコアの数式を決めない。

**進め方**：まず少数の人生を短い文章で書き、幼少期の選択、途中の変化、20歳時点、老後の関係を並べる。Q-011の「支える」「成果を優先する」「回復を試す」などは候補として比較する。同じ家庭で方針だけを変える比較と、子どもの個人差による比較を区別する。

**成果物**：各パターンのID、検証したい問い、共通条件、変える条件、代表的な選択、期待する結果の傾向をまとめた表。結末は期待として記し、パターンIDで強制する設計にしない。

**完了条件**：Q-013の主軸が決まり、各パターンが何の違いを確かめるか説明でき、全期間を含み、似た例の重複を整理している。親の幸福と子どもの成功の違いが、採用した例に現れる。

**関連**：Q-013、Q-011、Q-008の評価方針。SPEC S-010、S-009。

2026-09-13の結果：対象者（D-011）、親子の評価分離（D-012）、5本・共通家庭・親の評価5軸（D-013）が合意済み。[基本パターン](specs/verification.md)で比較の違いと全期間を定義し、[S-009](specs/ending.md)で評価方針を具体化した。Q-011の初版範囲は解決。

全ステップの根拠：[状態・行動](specs/core.md)（SP-02〜04）、[イベント](specs/events.md)（SP-05）、[成人後・評価](specs/ending.md)（SP-06）、[全期間の机上確認](specs/desk-check.md)（SP-07）、[CLI](specs/cli.md)（SP-08）、[検証計画](specs/verification.md)（SP-09）。以下の各ステップの説明は目的と完了基準であり、現在の未着手項目一覧ではない。

## SP-02：人生の時間軸と操作範囲

**決めること**：1ターン半年・全40ターン・20歳での移行は決定済み。0歳の開始季節、出生月・学年との対応、年代の区分、親の初期年齢と家庭構成、20歳での移行、老後編の開始と終了の構造。どの人物を直接操作し、どこからは本人の行動として計算するかも決める。老後の詳細な計算はSP-06で行う。

**進め方**：1本の時間軸に、通常のターン、年齢境界、育児から老後への移行、最期を置く。各段階に「プレイヤーが入力すること」「自動で起きること」「持ち越す情報」を書く。子ども1人の全40ターンとの対応を厳密に確認する。

**成果物**：年代表、進行段階と遷移条件、初期家庭の定義、操作対象の一覧。

**完了条件**：いつ誰が何を決めるか、何をもって1ターン（半年）が終わるか、20歳でいつ切り替わるかが一意に分かる。年代やターンの抜け・二重計上がない。

**関連**：Q-001、Q-008の進行構造。SPEC S-001、S-009。

## SP-03：パラメータと情報の見え方

**決めること**：親、子ども、家族関係、家計、祖父母に必要な最小の状態。固定の傾向、変動値、履歴、計算で導く値を区別する。誰に何が見えるか、どの行動が理解につながるかを定義する。

**進め方**：SP-01の違いを表現するために必要な項目から選ぶ。各項目について「何が増減させるか」「何の判断・結果に使うか」を線でつなぎ、使い道がない項目や重複を削る。子どもの真の状態と、親へ出す発言・観察例を対にする。

**成果物**：パラメータID、対象人物、意味、型・単位、範囲、初期値または生成規則、可視性、更新要因、利用先を持つ辞書。初期値・生成規則は具体的な仮値を置き、SP-07で調整する。最終評価に必要そうな健康や関係も、この段階で候補に含める。

**完了条件**：すべての項目に利用先があり、初期化できる。隠し状態には推測の手がかりがあり、固定の性格と一時的な疲れを混同しない。通常プレイとデバッグで見える項目が分かる。

**関連**：Q-002、Q-003、Q-008の引き継ぎ候補。SPEC S-002、S-003、S-006、S-009。

## SP-04：行動とターンの通常更新

**決めること**：働き方、支出、関わり、休息、支援の行動セット。利用条件、時間・費用、継続設定、確定や変更のタイミング。イベントがなくても働く収支・疲労・回復・成長・関係の更新式と処理順。

**進め方**：同じ初期状態で方針を変え、代表的な1ターン（半年）を手計算する。資金や時間の不足、上下限、無入力で継続する場合も試す。内部の変化とプレイヤーへ出す結果を対にし、「選ぶ前に何を知れるか」を整理する。CLIの厳密な形式に先立ち、文章だけの操作例を作る。

**成果物**：行動ID、入力値、条件、コスト、即時／継続効果、解除方法の一覧。順序を定めたターン処理と数値付きの入力・結果例。

**完了条件**：何も起きないターンも計算でき、資源不足や不正な選択の扱いが決まっている。費用と効果がいつ一度だけ適用されるか分かる。少なくとも方針間の利点と負担を説明できる。

**関連**：Q-002、Q-004、Q-005。SPEC S-001、S-002、S-004、S-006、S-007。

## SP-05：イベントと接続条件

**決めること**：各年代の少数のイベント、発生条件、選択肢、即時・遅延効果、後続の条件、再発・優先順位・同時発生の扱い。偶然と状態による必然を区別し、抽選のタイミングも決める。

**進め方**：基本パターンごとに「選択 → 状態変化 → 次の条件 → 観察や出来事」を並べる。別の選択、条件に届かない場合、イベントが発生しない場合もたどる。特定の年代を省かず、同じ仕組みを再利用できる題材を優先する。

**成果物**：安定したIDを持つイベント定義と接続表。各定義に条件、選択、効果量、発火時期、後続条件、表示文、再発規則を含める。老後へ渡す情報の利用先はSP-06で接続を完成させる。

**完了条件**：採用したイベントの条件と効果が計算可能で、発生／不発生、分岐先、繰り返しの扱いに空欄がない。回復経路があり、必須イベントの不発生でゲームが止まらない。

**関連**：Q-004、Q-005、Q-011。SPEC S-003、S-005、S-006、S-007、S-010。

## SP-06：進路・老後・幸福度

**決めること**：子どもの状態や意思から決まる最小の進路、20歳時点で持ち越す値、老後の時間刻みと更新、親それぞれの最期、最終幸福度の式・重み・表示。子どもの幸福と主体性をどう振り返るかも決める。

**進め方**：SP-01の評価方針へ戻り、途中で育った状態から結果を計算する。「資産だけ高い」「関係が良い」「成功していても関係が悪い」「回復した」などの入力を比較する。評価に必要なのに記録されていない状態はSP-03へ戻して追加する。将来の結末だけを直接書き換える処理にしない。

**成果物**：進路の判定、引き継ぎ表、老後の更新と少数の出来事、終了条件、評価式と内訳、結果文の生成条件。評価式にも初期の具体値を置く。

**完了条件**：すべての評価項目を育児・老後の状態や履歴から計算でき、各パターンが最期に到達する。既定の方針に反して、近居や孫だけが高幸福の必須条件になっていない。

**関連**：Q-008、Q-001、Q-011。SPEC S-009、S-010、S-007。

## SP-07：人生全体の通し確認と数値調整

**決めること**：PoC初版の数値セットと、未接続・矛盾の修正。現段階で固定するルールと、実装後に調整する仮説を明確にする。

**進め方**：基本パターンごとに、代表的な選択列から育児・進路・老後・最終評価までを机上でたどる。通常ターンの反復は同じ式で集計し、出来事、年齢境界、上下限、遅延効果が発生する箇所を数値で追う。省略した期間にも適用した式と前提を残す。選択を一つ変えた比較と、回復の経路を確認する。

**成果物**：初期条件、選択列、主要時点の内部状態と公開情報、最終評価を対応させた通し例。境界・例外の一覧、修正した箇所、実装後に確認する仮説。

**完了条件**：すべての基本パターンについて、最期までの必須処理と値が定義済み。行き止まり、未使用の状態、未定義の式がない。計算済みの例と未検証の期待が区別されている。完全なバランス調整や面白さの保証はこの段階の完了条件にしない。

**関連**：Q-001〜Q-005、Q-008、Q-011。SPEC S-001〜S-010。

## SP-08：CLIと技術契約

**決めること**：具体的なコマンド、引数・JSON入力、JSON出力と形式の版、行動ID、入力待ち／終了状態、エラーと終了コード、保存・再開・再生、状態リビジョン。実装言語、構成、乱数方式と記録に必要な情報を選ぶ。

**進め方**：SP-04の操作例とSP-07の通し例を、CLIの入出力例へ変換する。通常プレイの開始から最期までに加え、無効入力、再送、中断、読み取りの繰り返しを机上で確認する。テキスト表示とJSONの公開情報を照合し、保存や再生に必要な内部状態の欠落を点検する。

**成果物**：コマンド一覧、入出力スキーマ、正常・エラー例、保存形式、ログと再生の契約、技術選定の理由。構成説明が必要なら、この段階でarchitecture文書を作る。

**完了条件**：エージェントが表示文を推測して解析せずに、選択肢と必要入力を発見できる。呼び出し間の状態と乱数を保持でき、非対話操作で完走する手順が定義されている。不正入力と再送で状態を二重更新しない処理が明記されている。

**関連**：Q-006、Q-005の乱数・保存の具体化。SPEC S-008、S-011、S-012。

## SP-09：テストプレイ計画と初版SPECの確定

**決めること**：仕様ごとの検証方法、AIエージェントの方針、基本パターンとシードの組み合わせ、実行数・操作回数上限、停止と不具合の基準、記録形式、人が確認する項目。PoCの実装開始条件を最終点検する。

**進め方**：S-001〜S-012を一覧にし、それぞれに「入力条件 → 操作 → 期待結果 → 確認方法」を割り当てる。厳密な計算・再生の検証にはSP-07の具体例を使い、AIの自由な選択による探索プレイは結果を固定しない。公開情報だけのプレイと内部状態のデバッグを分ける。

**成果物**：検証ケースと仕様IDの対応表、AIプレイ手順、比較条件、結果報告の形式、実装対象になった初版SPEC。基本パターンから関連イベント・パラメータ・評価・検証ケースへの対応をたどれるようにする。

**完了条件**：次の条件をすべて満たしたら、P-SPEC完了としてP-TEXTへ進める。

- S-001〜S-012のPoCに必要な入力・処理・出力と受け入れ条件が具体的である。
- 基本パターンすべてが、途中で追加のルールを創作せずに最期までつながる。
- 必須の未決事項が解決し、残りは後続範囲または明記した調整仮説になっている。
- パラメータ、イベント、接続先、CLIの項目と操作に未定義の参照がない。
- 正常進行、資源不足、入力待ち、年代移行、終了、読み取り、再送、中断・再開・再生の確認方法がある。
- 計画、SPEC、決定記録が一致し、実装済み・プレイテスト済みとは誤記していない。

**関連**：Q-007、他のPoC必須Qの最終確認。SPEC S-001〜S-012。

## 差し戻しとバリエーション追加

- イベントが参照する状態が足りない場合はSP-03へ戻り、SP-04以降の影響箇所を見直す。
- 数値を変えても結末がほぼ同じ、または一つの方針だけが有利な場合は、SP-04〜SP-06の接続を見直す。
- 必要な操作や情報がCLIで表現できない場合は、SP-08から対応するゲーム仕様へ戻る。
- 実装後に新しいバリエーションを追加するときは、差分となる基本パターンを定め、影響するステップだけを再実施する。変更していない仕様を毎回作り直さない。

## 初版の最終点検（2026-09-13）

- S-001〜012：入力・処理・出力・受け入れ条件を分冊に定義済み。
- 人生全体：5本の全40期・成人後・最期を机上計算し、入力と状態を保存済み。
- 未決の必須ルール：Q-001〜008・011を仕様化。Q-009/010/012は後続範囲、Q-014は明記した調整仮説。
